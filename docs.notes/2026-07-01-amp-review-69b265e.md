# Amp Review: commit `69b265e`

Commit reviewed: `69b265ea4909653007c77b4372d469793ffc0a8e`  
Range reviewed: `4f298fa7e8ebff8b640b85e925e184c963fe9069..69b265ea4909653007c77b4372d469793ffc0a8e`

## Verdict: REJECT

The commit intentionally allows Google Play ACK placeholder payment rows with unknown amount/currency, but the payment read/API models were not updated to tolerate that nullable state.

## Blocking finding: ACK placeholder payments can break payment-history reads

### Evidence

- `migrations/100_allow_unknown_payment_amount_for_ack.sql` drops `NOT NULL` from `pay.payments.amount_cents`.
- `src/db/payments.rs::record_payment_with_purchase_token_tx` converts negative/missing amounts to `NULL`, filters `"UNKNOWN"` currency to `NULL`, and permits those values when `ack_required == true`.
- Google Play payment recording paths can now pass ACK-required rows with missing amount/currency placeholders:
  - `src/webhooks/processor/event_handlers.rs`
  - `src/services/google_play/product_lifecycle.rs`
- The read models still require non-null fields:
  - `Payment.amount_cents: i64`
  - `Payment.currency: String`
  - `PaymentHistoryEntry.amount_cents: i64`
  - `PaymentHistoryEntry.currency: String`
- `list_user_payments_keyset` selects `amount_cents, currency` directly from `pay.payments` into `PaymentHistoryEntry`.
- `src/handlers/payments.rs::PaymentDetail` also exposes non-null `amount_cents` and `currency`.

### Additional finding: second affected read path

- `get_user_payments` (`src/db/payments.rs:641`) does `SELECT * FROM pay.payments` decoded directly into `Payment` via `query_as::<_, Payment>`.
- `Payment` uses the same non-null `amount_cents: i64` / `currency: String` fields, so it has the same NULL-decode crash risk as `PaymentHistoryEntry`.
- This is a separate read path from `list_user_payments_keyset` — both need the same fix.

### Why this matters

A successful Google Play ACK placeholder row with unknown amount can later make `/api/v1/payments` fail SQLx decoding with `NULL` into `i64`/`String`. That turns a successfully recorded purchase/ACK candidate into a runtime 500 on payment history.

### Required fix

Choose one explicit contract:

1. **Nullable read/API contract**
   - Change payment read models and `PaymentDetail` to use `Option<i64>` / `Option<String>` for unknown amount/currency.

2. **Non-null API compatibility contract**
   - Keep API fields non-null, but `COALESCE(amount_cents, -1)` and `COALESCE(currency, 'UNKNOWN')` in payment read queries.
   - Document that these are display/API sentinels, while storage may remain nullable for ACK placeholders.

### Required regression test

Add coverage that records an ACK-required Google Play payment with missing amount/currency, then verifies payment history still returns successfully and represents the unknown amount/currency according to the chosen contract.
